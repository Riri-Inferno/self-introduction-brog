# ADR 0020: フロントエンドの API の型は、OpenAPI から自動で生成する

- **Date**: 2026-10-17
- **Status**: Accepted
- **Supplements**: [0014](0014-zod-schema-as-api-contract.md)

## Context

API の入出力は Zod のスキーマで定義し、そこから OpenAPI を作っている([0014](0014-zod-schema-as-api-contract.md))。フロントエンドでも、API のレスポンスに型を付けたい。

フロントエンドで型を手で書くと、API を変えたときに直し忘れる。直し忘れても型チェックは通るので、画面を動かすまで気づけない。

## Decision

### 生成の流れ

リポジトリのルートで `npm run gen:api` を打つと、次の2つを順に行う。

1. バックエンド:サーバーを起動せずに、`buildApp` から OpenAPI を書き出す → `backend/openapi.json`
2. フロントエンド:`openapi-typescript` で型を作る → `frontend/src/api/schema.d.ts`

- DB は使わない。ユースケースにはフェイクを渡す
- 同じスキーマからは、同じファイルができる。何度打っても、差分が出るのはスキーマを変えたときだけ
- 生成した2つのファイルはコミットする
- ルートの package.json は、このスクリプトを置くためだけに作る。依存パッケージは入れない

### API の呼び出し

フロントエンドでは `openapi-fetch` で API を呼ぶ。生成した型を読み、パス・クエリ・レスポンスに型が付く。

### 生成し忘れを防ぐ

- バックエンドの単体テストで、今のスキーマから作った OpenAPI と、コミット済みの `backend/openapi.json` が同じかを比べる。API を変えて `gen:api` を忘れると、`npm test` が失敗する
- `gen:api` を流し直してフロントの型が変わり、使っている側と合わなくなれば、フロントエンドの型チェックで失敗する

### 検討した選択肢

| 案 | 内容 | 採否 |
|----|------|------|
| A | OpenAPI から型を生成する(`openapi-typescript` + `openapi-fetch`) | 採用 |
| B | バックエンドの Zod のスキーマを、フロントエンドから直接 import する | 不採用(フロントエンドがバックエンドのコードに依存する。OpenAPI を API の取り決めとして使う意味がなくなる) |
| C | フロントエンドで型を手で書く | 不採用(直し忘れに気づけない) |
| D | API を呼ぶ関数まで生成するツール(Orval など) | 不採用(今の規模では生成物が多すぎる。A は型だけを生成し、呼び出しは小さなライブラリで済む) |

## Consequences

- API のスキーマを変えたら、`npm run gen:api` を打つ。忘れたら `npm test` で気づける
- 生成物がコミットに入るので、API の変更がフロントエンドの型の差分としても見える
- GitHub Actions で、型チェックとテスト(生成し忘れの確認を含む)を流すことも考えている。入れるときは別に決める
