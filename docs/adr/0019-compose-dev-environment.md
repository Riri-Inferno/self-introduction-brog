# ADR 0019: 開発環境は docker compose up 1回で、DB・バックエンド・フロントエンドを立てる

- **Date**: 2026-10-17
- **Status**: Accepted

## Context

今の docker-compose.yml には DB しかなく、バックエンドはホストで `npm run dev` を打って起動している。フロントエンド(Vite + React)を足すと、起動するものが3つになり、手順が増える。

ローカルの開発環境を、1回のコマンドで立てられるようにしたい。

前提と制約は次のとおり。

- リポジトリは WSL から `/mnt/c`(Windows 側のファイル)を見ている。この場所では、ファイルの変更がコンテナに通知されないことがある
- バックエンドの設定は `backend/.env` から読む([0016](0016-env-config-validation.md))。今の `.env` は、ホストで動かすときの値(DB は `localhost:5432`)になっている
- テスト(単体・統合)は、今までどおりホストで流す([0017](0017-testing-strategy.md))

## Decision

### 構成

`docker compose up` で、次の3つを起動する。

| サービス | 中身 | ポート |
|----------|------|--------|
| `db` | postgres:18(今のまま) | 5432 |
| `backend` | `backend/Dockerfile`(node:22)。`tsx watch` で起動 | 3000 |
| `frontend` | `frontend/Dockerfile`(node:22)。Vite の開発サーバー | 5173 |

- Dockerfile は開発用だけを作る。本番用の構成は、デプロイ先を決めるときに別に考える
- ソースはホストのフォルダをそのままマウントし、保存したら反映されるようにする
- `node_modules` はコンテナ専用の volume に置く。Windows 側と Linux 側で、Prisma や esbuild のバイナリが混ざらないようにするため
- 起動時に `npm install` を流す。package.json が変わっても、イメージを作り直さずに追いつく
- ファイルの変更は、ポーリング(定期的に見に行く)で検知する。`/mnt/c` でも、WSL 側でも、ほかの OS でも同じように動くようにするため

### 環境変数

- compose の `env_file` で、まず `backend/.env.example` を読み、`backend/.env` があればその値で上書きする(`.env` はなくてもよい)
- コンテナの中でだけ変わる値は、compose の `environment` で指定する。`env_file` より優先される

| 項目 | ホストで動かすとき(`.env`) | コンテナ(`environment`) |
|------|------------------------------|---------------------------|
| `DATABASE_URL` | `localhost:5432` | `db:5432`(コンテナ同士はサービス名で呼ぶ) |
| `HOST` | `127.0.0.1` | `0.0.0.0`(コンテナの外から届くようにする) |

`.env` は今のまま、ホストで動かすとき用の内容にしておく。

### API への接続

フロントエンドからは `/api` で呼ぶ。開発中は Vite のプロキシで `/api` を `http://backend:3000` に流す。ブラウザから見ると同じオリジンになるので、CORS の設定は要らない。

### DB のマイグレーション

- バックエンドの起動時に `prisma migrate deploy` を流す。未適用のマイグレーションを当てるだけなので、何度流しても同じ結果になる
- マイグレーションを作る `prisma migrate dev` は、今までどおりホストで手で打つ
- seed は起動時に流さない。手で打つ([setup.md](../setup.md))

### 検討した選択肢

環境変数の渡し方:

| 案 | 内容 | 採否 |
|----|------|------|
| A | `env_file` で `.env.example` を読み、`.env` があれば上書きする。コピーはしない | 採用 |
| B | 起動時に `.env` がなければ `.env.example` からコピーする | 不採用(`.env.example` に項目を足しても、作成済みの `.env` には反映されない) |
| C | 起動時に毎回 `.env.example` からコピーする | 不採用(手で変えた `.env` の値が、起動のたびに消える) |

ファイルの変更の検知:

| 案 | 内容 | 採否 |
|----|------|------|
| A | ポーリングで検知する | 採用 |
| B | OS の通知(inotify)で検知する | 不採用(`/mnt/c` のマウントでは通知が届かないことがある) |

## Consequences

- `docker compose up` だけで、DB・API・画面がそろう
- ホストで `npm run dev` を打って動かす方法も、今までどおり使える。ただし、コンテナのバックエンドと同時には動かせない(ポート 3000 がぶつかる)
- ポーリングの分、CPU を少し使う。使わないときは `docker compose down` で止める
- `/mnt/c` に置いている間は、ファイルの読み書きが遅い。速くしたいときは、リポジトリを WSL 側(`~/`)に置く
- 初回の起動は、`npm install` の分だけ時間がかかる
