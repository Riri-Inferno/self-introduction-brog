# ADR 0021: フロントエンドの部品は Atomic Design の5層に分け、API はページだけが呼ぶ

- **Date**: 2026-10-31
- **Status**: Accepted

## Context

フロントエンドの画面を作り始める。閲覧画面には、プロフィール、スキル、経歴など、似た見た目の部品が何度も出てくる(名前、バッジ、カードなど)。部品の分け方と置き場所を決めておかないと、同じ見た目を画面ごとに書き直すことになる。

また、API の呼び出しや、読み込み中・エラーの扱いがあちこちの部品に散らばると、部品を別の画面で使い回せなくなる。

## Decision

### 5つの層

Atomic Design に沿って、部品を5つの層に分ける。

| 層 | 役割 | 例 |
|----|------|----|
| atoms | これ以上分けられない最小の部品 | ボタン、バッジ、見出し |
| molecules | atoms を組み合わせた小さな部品 | アバター(画像と、出ないときの1文字目)、言語の切り替え |
| organisms | 画面の中の、意味のあるひとまとまり | プロフィールのカード、スキルの一覧 |
| templates | 枠だけを決める。どこに何を置くか | ヘッダー・本文・フッターの並び |
| pages | API を呼び、templates に中身を渡す | 閲覧画面のトップ |

- 部品は、自分より下の層だけを import する。上の層や、同じ層の別の部品に頼らない形を基本にする
- templates はデータを持たない。中身は pages から `children` などの props で受け取る(Vue の `<slot>` に当たる)

### API を呼ぶのは pages だけ

- API の呼び出し、読み込み中・エラーの書き分けは pages で行う
- templates から atoms までは、表示する値を props で受け取るだけにする。API のことを知らないので、ダミーの値を渡せばどの画面でも使える
- 部品の中だけで完結する状態(画像の読み込みに失敗したか、など)は、その部品が `useState` で持ってよい

### 取得の処理はカスタムフックに切り出す

API を呼ぶ処理は、`use` で始まる関数(カスタムフック)に切り出す。Vue の composable に当たる。

- pages は `const { profile, error } = useProfile(locale)` のように呼ぶだけにする
- 後で TanStack Query を入れるときは、フックの中身だけを差し替える。pages は変えない

### 置き場所

```
frontend/src/
├── api/            OpenAPI から生成した型(ADR 0020)
├── hooks/          カスタムフック
├── components/
│   ├── atoms/
│   ├── molecules/
│   ├── organisms/
│   └── templates/
└── pages/
```

### 検討した選択肢

| 案 | 内容 | 採否 |
|----|------|------|
| A | Atomic Design の5層(templates を含む) | 採用 |
| B | templates を省いた4層 | 不採用(枠の置き場所がなくなり、pages に並びとデータの扱いが混ざる) |
| C | 機能ごとにフォルダを分ける(`features/profile/` など) | 不採用(画面が少ないサイトでは、機能ごとに分けるほどの量がない。見た目の部品の使い回しを優先する) |

## Consequences

- 新しい部品を作るときは、どの層に置くかを決める。迷ったら、小さい層に置いて、必要になったら組み合わせる
- 層の境目(molecules と organisms など)は人によって判断が分かれる。迷ったものは、置いた理由をコメントに残す
- pages から深い部品へ値を渡すとき、途中の層が値を受け渡すだけになることがある(props のバケツリレー)。今のサイトの規模では問題にしない。困ったら別に決める
