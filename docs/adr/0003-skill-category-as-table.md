# ADR 0003: カテゴリ類はテーブルにし、スキルは親子関係を持たない

- **Date**: 2026-10-15
- **Status**: Accepted

## Context

スキルは「OS」「クラウド」「IaC」「CI/CD」のようなカテゴリに分けて表示する。カテゴリは今後増減する可能性があり、編集画面から変更したい。

職務経歴書の環境欄には `AWS(ECS Fargate / ALB / RDS …)` のように、クラウドとその中のサービスが入れ子になった書き方がある。これを `Skill` の親子関係(AWS > ECS Fargate)として持つかどうかを検討した。

## Decision

### カテゴリはテーブルにする

カテゴリは Enum にせず、`SkillCategory` テーブル(と翻訳テーブル)で持つ。編集画面から増減できる。

### スキルは並列のままにし、親子関係を持たない

`Skill` に親子関係(`parentId`)は持たせない。AWS のサービス群をまとめたい場合は、カテゴリに「AWS」「Azure」「GCP」を作って分ける。

### 検討した選択肢

| 案 | 内容 | 採否 |
|----|------|------|
| A | スキルは並列。まとまりはカテゴリで表す | 採用 |
| B | `Skill.parentId` で親子関係を持つ | 不採用(今は不要。理由は下記) |
| C | カテゴリを Enum にする | 不採用(カテゴリを変えるたびにマイグレーションが要る) |

案 B を採用しなかった理由は次のとおり。

- 編集画面で親を選ぶ UI、循環参照(A の親が B、B の親が A)の防止、ツリーの組み立てが要り、実装が重くなる
- カテゴリを自由に増やせるので、案 A でも同じまとまりを表せる
- 必要になったら `parentId Int?` を後から足せる。nullable なので既存データに影響しない

## Consequences

- カテゴリの追加・名前変更・並べ替えは編集画面だけでできる
- 「AWS > ECS Fargate」のような入れ子の表示はできない。必要になったら案 B を新しい ADR で検討する
- 案 B に切り替えるときの作業は次のとおり。DB の変更は軽く、重いのは編集画面と API
  - DB: `parentId Int?` を足すマイグレーション1本。nullable なので既存データの移行は要らない
  - データ: 既存のスキルに親を設定し直す(例: `ECS Fargate` の親を `AWS` にする)。編集画面から行える
  - 編集画面と API: 親を選ぶ UI、循環参照の防止、ツリー表示の組み立てを作る
- 使用中のカテゴリは削除できない(`onDelete: Restrict`)。先にスキルを別カテゴリへ移す必要がある
