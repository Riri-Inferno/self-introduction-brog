# ADR 0006: 日時は timestamptz で UTC 保存し、年月だけの日付は1日で保存する

- **Date**: 2026-10-15
- **Status**: Accepted

## Context

データには2種類の時刻情報がある。

- 作成日時・更新日時・記事の公開日時: 時刻まで意味がある
- 在籍期間・案件期間・資格の取得日など: 職務経歴書では「2023年4月」のように年月までしか書かない

サイトの閲覧者は主に日本からアクセスするが、DB とサーバーのタイムゾーンに依存しない形にしたい。

## Decision

### 日時は timestamptz で UTC 保存する

`createdAt` / `updatedAt` / `publishedAt` は `@db.Timestamptz(3)` にする。

層ごとの扱いは次のとおり。

| 層 | 扱い |
|----|------|
| DB | UTC で保存する |
| バックエンド | UTC のまま扱う。タイムゾーンの変換はしない。API は ISO 8601(末尾 `Z`)で返す |
| フロント | 受け取った UTC を、閲覧者のローカルタイムゾーンに変換して表示する |

### 年月だけの日付も Date 型で持ち、日は1日で保存する

在籍期間などは `@db.Date` で持つ。年月しか分からない場合は、日を 1 日にして保存する(例: 2023年4月 → `2023-04-01`)。表示側で `yyyy/MM` に整形する。

Date 型の値はタイムゾーンの変換をしない。Prisma は Date 型を UTC の 0 時の `Date` として返す。これをそのまま JSON にすると `2023-04-01T00:00:00.000Z` になり、フロントでローカル時刻に変換すると、UTC より西のタイムゾーンでは前日、つまり月初なら前月として表示される。

これを防ぐため、API は Date 型を時刻なしの `YYYY-MM-DD` 文字列(例: `"2023-04-01"`)で受け渡しする。OpenAPI の `type: string, format: date`(RFC 3339 の full-date)と同じ形式で、日付だけの値を JSON で扱うときの一般的な書き方である。

| 層 | 扱い |
|----|------|
| DB | `date` 型で保存する |
| バックエンド | レスポンスでは `Date` を `YYYY-MM-DD` に変換して返す。リクエストは Zod で `YYYY-MM-DD` 形式を検証してから `Date` に変換する |
| フロント | 文字列から年月を取り出して表示する。`Date` に変換してローカル時刻として扱わない |

`endedAt` が NULL のときは「現在も継続中」(在籍中・在学中など)を表す。

### 検討した選択肢

| 案 | 内容 | 採否 |
|----|------|------|
| A | 年月も Date 型で持ち、日は1日に揃える | 採用 |
| B | `"2023-04"` のような文字列で持つ | 不採用(日付としての比較や範囲チェックがしにくい) |
| C | 年と月を別々の Int カラムで持つ | 不採用(カラムが倍になり、比較の書き方も複雑になる) |
| D | 日時を timestamp(タイムゾーンなし)で持つ | 不採用(サーバーの設定によって解釈が変わる) |

## Consequences

- 日付の比較やソートが Date 型のまま行える
- 日を1日に揃えないデータが混ざると、比較やソートの結果がずれる。登録時に揃える必要がある
- 日時と日付で API の形式が違う(日時は末尾 `Z` 付き、日付は `YYYY-MM-DD`)。形式を見れば、ローカル変換するかどうかを区別できる
- バックエンドに `Date` と `YYYY-MM-DD` を相互に変換する処理が要る
- 「年まで分かる」「日まで分かる」のような精度の違いは区別できない
