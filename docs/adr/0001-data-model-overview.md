# ADR 0001: データモデルの全体構成

- **Date**: 2026-10-15
- **Status**: Accepted

## Context

自己紹介サイトでは、経歴・スキル・個人開発などを公開する。内容は編集画面から自分で更新する。


## Decision

次のモデルで構成する。定義は `backend/prisma/schema.prisma` にある。

| 領域 | モデル | 備考 |
|------|--------|------|
| プロフィール | `Profile` | 1行だけ持つ。`id` は常に 1 で upsert する |
| スキル | `SkillCategory` / `Skill` | [0003](0003-skill-category-as-table.md)、[0004](0004-skill-master-and-join-tables.md) |
| 職務経歴 | `Career`(勤務先) 1 - N `Assignment`(案件) | 案件は期間が重なってもよい |
| 個人開発 | `Project` | 個別ページ用に `slug` を持つ。`endedAt` が NULL なら継続中 |
| 学歴 | `Education` | 経歴とは別テーブル |
| 資格 | `Certification` | `expiresAt` が NULL なら期限なし |
| 外部リンク | `SocialLink` | [0009](0009-social-link-host-detection.md) |
| ブログ記事 | `Post` | 近況や技術メモ |

### 個人情報は持たない

住所・電話番号・メールアドレス・生年月日・性別のカラムは作らない。公開サイトに出さない情報は、DB にも入れない。

### 職務経歴は勤務先と案件の2階層にする

職務経歴書と同じく、1社の下に複数の案件が並ぶ形にする。案件ごとの本文は「プロジェクト内容」「担当業務」「実績・取り組み」の3つに分け、それぞれ Markdown で持つ。役割(例: リーダー)は短い文字列で別に持ち、人数などは本文に書く。

### 学歴は経歴と別テーブルにする

経歴は会社 URL、配下の案件、使用技術を持つ。学歴は学校名・学部・在籍状況だけで、配下の案件はない。1つのテーブルにまとめると、学歴の行で案件まわりの項目が空になるため分ける。

在籍状況(卒業 / 中途退学など)は、翻訳テーブルの `status` に自由入力の文字列で持つ。Enum にしないのは、表示する文言をそのまま編集できるようにするため。

### ブログ記事を持つ

近況や技術メモを書く場所として `Post` を持つ。並び順は公開日時で決めるので、`sortOrder` は持たない。技術タグは今は付けない。

### 見た目の制御はデータに持たせない

レイアウトや色などはフロントで決める。`Skill.isFeatured` のような「主要かどうか」の情報は持つが、それをどう見せるかはフロントが決める。

### 並び順

`sortOrder` は小さい順で、編集画面から並べ替える。同じ値が並んだときの2つ目の並び順は、API のクエリで指定する(例: `[{ sortOrder: 'asc' }, { startedAt: 'desc' }]`)。

### 検討した選択肢

| 案 | 内容 | 採否 |
|----|------|------|
| A | 経歴と学歴を別テーブルにする | 採用 |
| B | 経歴と学歴を1テーブルにして種別で分ける | 不採用(学歴の行で案件まわりの項目が空になる) |
| C | ブログは外部(DevIO など)に書き、`SocialLink` で誘導するだけにする | 不採用(近況をこのサイトに書きたい) |

## Consequences

- 公開したくない個人情報が DB に入らないので、API で誤って返す心配がない
- 職務経歴書の構成をそのまま入力できる
- `Profile` が1行だけであることは Prisma の schema では表せないので、CHECK 制約で守る([0010](0010-check-constraints-in-migration.md))
- 経歴と学歴を時系列で1つの一覧に混ぜて表示したい場合は、API かフロントで2つを合わせる必要がある
