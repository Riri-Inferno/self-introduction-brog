# ADR 0002: 日英対応は翻訳テーブル方式にする

- **Date**: 2026-10-15
- **Status**: Accepted

## Context

サイトは日本語と英語に対応する。会社名・案件名・自己PRなど、言語ごとに内容が変わるテキストが多い。

将来、言語を増やす可能性もある。

## Decision

言語ごとのテキストは `<Model>Translation` テーブルに分ける。

- 主キーは `(親ID, locale)`。言語ごとに1行持つ
- 言語に依存しない値(日付、URL、並び順、公開フラグなど)は親テーブルに置く
- 技術名や外部リンクのサービス名のような固有名詞は翻訳しない(`Skill`、`SocialLink` は翻訳テーブルを持たない)
- 英訳しない記事などは `ja` の行だけでもよい

`locale` は Enum にせず、`VarChar(8)` の文字列(`'ja'` | `'en'`)で持つ。値は Zod で検証し、DB でも CHECK 制約で守る([0010](0010-check-constraints-in-migration.md))。

### 検討した選択肢

| 案 | 内容 | 採否 |
|----|------|------|
| A | 翻訳テーブルに分ける | 採用 |
| B | `titleJa` / `titleEn` のように言語ごとのカラムを並べる | 不採用(言語を増やすたびに全テーブルにカラム追加が要る) |
| C | `{ ja: "...", en: "..." }` の JSON カラムで持つ | 不採用(必須チェックや型付けを DB と Prisma で効かせにくい) |
| D | `locale` を Enum にする | 不採用(言語を増やすたびにマイグレーションが要る) |

## Consequences

- 言語を増やすときは、行を追加するだけで済む(CHECK 制約の値の追加は要る)
- 取得のたびに翻訳テーブルとの JOIN(Prisma の `include`)が要る
- 英語の行がないときにどう表示するか(日本語で代替するか、項目ごと出さないか)は API で決める必要がある
- 翻訳だけを更新しても親の `updatedAt` は変わらないので、別途ルールを決めた([0007](0007-updated-at-propagation.md))
