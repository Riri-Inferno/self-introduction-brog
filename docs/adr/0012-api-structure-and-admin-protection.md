# ADR 0012: API は用途ごとにパスを分け、管理用 API はインフラとアプリの両方で保護する

- **Date**: 2026-10-15
- **Status**: Proposed

## Context

画面は、一般ユーザーが見る閲覧画面と、自分だけが使う編集画面の2つがある。バックエンドは1つで、どちらの画面も同じ API サーバーを使う。

管理用 API は書き込みができるので、自分以外が使えないように保護する必要がある。当初はインフラ側だけで保護し、アプリ側の認証は後回しにする予定だった。理由は次の2つである。

- まずアプリ本体の実装を進めたかった
- 自前でログイン機能を作るより、Cloudflare や Google などの外部認証を使うほうが堅牢になる

ただし、外部認証を使うことは、アプリ側で保護しない理由にはならない。インフラ側だけで保護すると、次の場合に管理用 API がそのまま使えてしまう。

- 認証プロキシを経由せず、オリジンに直接アクセスされた場合
- インフラの設定ミスで、認証が外れた場合

## Decision

### パスで用途を分ける

| パス | 用途 | 認証 | 操作 |
|------|------|------|------|
| `/api/public/*` | 閲覧用 | なし | 読み取りのみ(GET だけを登録する)。公開済みのデータだけ返す([0005](0005-publish-flag.md)) |
| `/api/admin/*` | 管理用 | 必須 | 作成・更新・削除。下書きを含む全件を扱う |

OpenAPI は `public` と `admin` のタグで区別する。

### 管理用 API はインフラとアプリの両方で保護する

1. インフラ: 編集画面と管理用 API の前に、外部の認証プロキシ(Cloudflare Access など)を置く。自前のログイン機能は作らない
2. アプリ: 認証プロキシがリクエストに付ける署名付き JWT を、管理用 API で検証する。署名、`aud`、有効期限、メールアドレスが自分のものかを確かめる。Cloudflare Access なら `Cf-Access-Jwt-Assertion` ヘッダーの JWT を、公開鍵(JWKS)で検証する
3. 検証に必要な設定(公開鍵の URL、`aud` など)がないときは、管理用 API のリクエストをすべて拒否する。設定漏れで保護が外れないようにするため
4. ローカル開発では、環境変数で JWT の検証を無効にできる。本番(`NODE_ENV=production`)では無効にできないようにする

アプリ側の検証は、管理用 API のルート全体にかかる Fastify の `onRequest` フックに置く。ルートごとに書かない。

### 実装の順番

アプリ本体を先に作り、その間はローカルでだけ管理用 API を使う。外部に公開する前に、インフラの認証プロキシとアプリ側の JWT 検証を入れる。

### 検討した選択肢

| 案 | 内容 | 採否 |
|----|------|------|
| A | インフラの認証プロキシと、アプリでの JWT 検証の両方で保護する | 採用 |
| B | インフラの認証プロキシだけで保護する | 不採用(プロキシを経由しないアクセスや設定ミスを防げない) |
| C | アプリに自前のログイン機能(パスワード、セッション)を作る | 不採用(外部認証より堅牢にするのが難しく、実装量も多い) |

## Consequences

- インフラかアプリのどちらか一方の保護が外れても、管理用 API は使えない
- アプリ側は JWT を検証するだけで済み、パスワードやセッションを管理しなくてよい
- 認証プロキシのサービス(Cloudflare Access、Google など)はまだ決めていない。決めたら Status を Accepted にし、ヘッダー名などを確定する
- ローカル開発で検証を無効にする設定が、本番で誤って有効にならないようにする必要がある
